# Подготовка к защите ВКР — вероятные вопросы и ответы

Проект: **Wanderlog** — туристическое offline-first PWA (Nuxt 3 / Vue 3 / TypeScript).
Стек: Drizzle ORM + Turso (LibSQL/SQLite), Pinia, Mapbox GL / MapLibre, Better-Auth,
S3, Workbox/@vite-pwa, Web Push, OpenAI-совместимый AI для маршрутов.

Документ построен по порядку слайдов презентации: для каждого раздела — вероятные
вопросы комиссии, готовые ответы и «подводные камни».

---

## 1. Логическая модель БД (по доменам)

**Факты:** Drizzle ORM + SQLite/LibSQL (Turso), ~15 таблиц, 5 доменов: Auth;
Дневник (`location` → `locationLog` → `locationLogImage`); Соцлента
(`post`/`postComment`/`postLike`); AI-маршруты (`aiRouteSession` → `aiRouteVariant`
→ `aiRoutePoint` + `aiRouteMessage`/`aiRouteEvent`); Уведомления/сохранение.

**Вопросы и ответы:**

- **Почему модель разбита на домены?**
  Подход bounded context (DDD): каждый домен независим, связи через `userId`.
  Упрощает понимание, изоляцию изменений и масштабирование. Цельная ER-диаграмма из
  15 таблиц нечитаема — поэтому домены показаны раздельно.

- **Почему SQLite/Turso, а не PostgreSQL?**
  Turso (LibSQL) — распределённый SQLite на edge: низкая латентность чтения, простой
  деплой, бесплатный тариф. Drizzle даёт типобезопасность и лёгкую миграцию на Postgres.

- **Зачем `locationLogImage` дублирует координаты (`publicLat/publicLong`) и зачем
  отдельная `post`?**
  Разделение приватного и публичного. Фото в дневнике приватно; при публикации
  создаётся `post`-обёртка с отдельной публичной геопозицией и `visibility`. Можно
  показывать приблизительную локацию в ленте, не раскрывая точную (`locationAccuracy`,
  `locationSource`).

- **Что обеспечивает целостность данных?**
  FK с `onDelete: cascade`; уникальные индексы (`UNIQUE(postId, userId)` — один лайк;
  `UNIQUE(name, userId)` — уникальность места у пользователя); таблица `idempotencyKey`
  против повторной обработки запросов.

**Подводный камень:** про нормализацию — схема в 3НФ, денормализация координат в
`post` сделана осознанно ради скорости чтения ленты.

## 2. Стриминг точек на карте + генерация маршрута

**Факты:** маршрут генерирует AI (OpenAI-совместимый API). Сервер
(`server/api/ai/route.post.ts`) отдаёт **SSE** через `TransformStream`; клиент
(`composables/use-ai-route-session.ts`) читает `ReadableStream.getReader()`, парсит
блоки `data: {...}\n\n` и добавляет точки на карту (Mapbox GL) по мере поступления.
Геометрия — **cheapest insertion** + **формула Хаверсина**; реальные пешеходные дороги —
Mapbox Directions API. Лимит 20 генераций/сутки. События валидируются Zod.

**Вопросы и ответы:**

- **Почему SSE, а не WebSocket?**
  Поток односторонний (сервер → клиент). SSE проще: поверх HTTP, авто-переподключение,
  не нужен отдельный протокол. WebSocket избыточен для однонаправленных событий.

- **Как работает алгоритм вставки точки?**
  Cheapest Insertion: для новой точки перебираем рёбра маршрута, считаем удорожание
  `dist(A,новая) + dist(новая,B) − dist(A,B)`, вставляем где минимально. Расстояния —
  Хаверсин (сферическое, радиус 6371 км).

- **Это TSP — почему не точный алгоритм?**
  TSP NP-полная, экспоненциальна. Cheapest insertion — полиномиальная эвристика,
  результат типично в пределах 10–15% от оптимума; для прогулочного маршрута достаточно.

- **Что если AI вернёт некорректные данные?**
  Каждое событие валидируется Zod (`RouteEventEnvelopeSchema`). Невалидное → `route.warning`,
  поток не ломается. Лимит 20/сутки защищает от абьюза/расходов.

- **Почему Mapbox?**
  WebGL-рендеринг (плавность при многих точках), 3D-глобус, Directions API. Есть и
  MapLibre/Yandex как альтернативы.

**Подводный камень:** AI даёт *точки интереса*, а **порядок и геометрию** маршрута
считаете вы (Хаверсин + cheapest insertion) — подчёркивайте свой вклад.

## 3. Сохранение фото через IndexedDB — три шага

**Факты** (`composables/use-offline-queue.ts`):
1. **Persistent storage + проверка квоты** — `requestPersistentStorage()`, отказ при >80%.
2. **Сохранение blob в IndexedDB** (store `photo_blobs`, ключ `opId`) + SHA-256 checksum.
3. **Метаданные операции** в `pending_operations` (статус `pending`, `blobRef`, checksum)
   → асинхронная отправка `processPhotoOp`.

Онлайн: blob из IDB → подпись сервера → загрузка в S3 → уведомление сервера →
удаление blob и операции из IDB.

**Вопросы и ответы:**

- **Зачем IndexedDB, а не сразу загрузка?**
  Оффлайн-устойчивость: в путешествии часто нет сети. Фото сжимается (до 1000px),
  хранится локально и гарантированно отправляется при подключении.

- **Зачем SHA-256?**
  Верификация целостности blob и защита от дублей.

- **Зачем две записи (blob и метаданные раздельно)?**
  Разделение тяжёлых бинарных данных и лёгких метаданных: по `pending_operations`
  быстро строится очередь и UI без чтения мегабайтных blob'ов. Связь по `opId`.

- **Что если приложение закроется между шагами?**
  Каждый шаг атомарен (IDB-транзакция). Записанная операция подхватится при старте.
  «Осиротевший» blob без метаданных — известная зона улучшения.

## 4. Service Worker

**Факты** (`public/wanderlog-sw.js`, @vite-pwa/nuxt + Workbox, `injectManifest`):
- **Precache** app shell при install.
- **StaleWhileRevalidate** — статика (`/_nuxt/`, иконки, шрифты).
- **CacheFirst** — изображения (LRU: 200 записей, 30 дней).
- **NetworkFirst** — GET `/api/` (таймаут 4с, фолбэк на кэш).
- **Background Sync** (`Queue`) — POST/PUT/DELETE оффлайн, обработка 401/409/422;
  Safari — ручной триггер через `postMessage`.
- Оффлайн-навигация → prerendered shell `/offline`.

**Вопросы и ответы:**

- **Чем отличаются стратегии и почему так?**
  Статика меняется редко → SWR. Картинки тяжёлые и неизменяемы → CacheFirst+LRU.
  API должно быть свежим → NetworkFirst с таймаутом (нет сети 4с → кэш).

- **Как обрабатываются оффлайн-мутации?**
  Workbox Background Sync: запрос в очередь, при сети ОС запускает синхронизацию.
  Коды: 401 → ждём ре-логина, 409 → конфликт, 422 → невалидно.

- **Что видит пользователь оффлайн?**
  Навигация → `/offline`, карта монтируется из IndexedDB-тайлов.

**Подводный камень:** SW-кэш (Cache API через `fetch`) и IndexedDB (фото/тайлы вручную) —
разные слои. Большие blob'ы фото и тайлы карт SW НЕ кэширует — они в IndexedDB.

## 5. Оффлайн-карта в IndexedDB

**Факты:** регион (bbox + zoom) → перечисление тайлов (Mercator, генератор) →
параллельная загрузка (CONCURRENCY=4) с retry (3 попытки, backoff 250→500→1000мс) →
пакетная запись (BATCH_SIZE=24) в БД `wanderlog-offline` (stores `regions` + `tiles`,
тайл = `Uint8Array` PBF/MVT). Источник — PMTiles. Удаление региона — каскад по индексу
`regionId`. Проверка квоты, `purgeOnQuotaError`.

**Вопросы и ответы:**

- **Сколько весит карта города, не переполнит ли хранилище?**
  Зависит от bbox и max zoom; векторные PBF компактны. Перед загрузкой считается
  `totalTiles`, есть проверка квоты (>80% отказ) и `purgeOnQuotaError`.

- **Зачем батчи и параллелизм?**
  Параллельно 4 тайла — быстрее; запись 24 в одну транзакцию — меньше накладных
  расходов; retry с backoff — устойчивость к нестабильной сети.

- **Почему векторные тайлы (PMTiles/MVT), а не PNG?**
  Легче по объёму, рендеринг на клиенте (смена стиля), Range-запросы из одного архива.

- **Почему отдельная БД для карт?**
  Изоляция жизненных циклов: разные схемы, версии, стратегии удаления. Каскадное
  удаление региона не затрагивает фото.

## 6. Результаты тестирования

**Факты:** 58 файлов, **319 серверных тестов** на встроенном `node:test` (без внешних
зависимостей). Нагрузочное: 7 сценариев, Phase 13 — 100 VU / 10 мин / 1000 фото /
5000 лайков. Пороги: read p95 ≤ 800мс, write p95 ≤ 1500мс, error rate ≤ 1%.
CI (GitHub Actions) гоняет только lint (Node 18/20/22). UI/E2E-тестов и coverage НЕТ.

**Вопросы и ответы:**

- **Почему нет E2E и тестов компонентов?** (вероятен острый вопрос)
  Сознательный приоритет на серверную логику и контракты (валидация, безопасность,
  авторизация) — там основная бизнес-логика и риски. UI-тесты (Playwright/Vitest) —
  направление дальнейшего развития. Не выдавать отсутствие за наличие.

- **Почему тесты не в CI?**
  Сейчас в CI только lint; `npm run test:server` локально. Зона улучшения — добавить
  тестовый job (нужны секреты БД).

- **Что показывают нагрузочные тесты?**
  Назвать конкретные цифры своего прогона. ПЕРЕД ЗАЩИТОЙ запустить и записать реальные
  числа: `npm run test:server`, `npm run load:e2e:dry-run`.

**Подводный камень:** не преувеличивать покрытие. «319 серверных тестов покрывают
контракты, безопасность и оффлайн-логику» — а не «проект полностью покрыт».

## 8. Заключение

- **Новизна:** комплексное offline-first PWA для туризма — стриминговое AI-построение
  маршрута + надёжная оффлайн-синхронизация фото (гарантия доставки) + оффлайн-карты.
- **Планы развития:** E2E-тесты и прогон тестов в CI, coverage, очистка осиротевших
  blob'ов, миграция на Postgres при росте, оптимизация TSP для длинных маршрутов.
- **Применимость:** туристические сервисы, путешествия без покрытия, дневник + соцсеть.

## Общие советы

- На каждый «почему» — обоснование выбора через альтернативы (SSE vs WS, SQLite vs
  Postgres, векторные vs растровые тайлы).
- Разделять «что делает библиотека/AI» и «что реализовали вы» (алгоритмы маршрута,
  очередь оффлайн-операций, downloader тайлов — ваш код).
- Слабые места (UI-тесты, CI) признавать честно и переводить в «направления развития».
